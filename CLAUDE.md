# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Car dealership vehicle management system: browse the inventory for sale, classified by category, with name (make), model, year and price as the core fields. Vite + React 19 + TypeScript front end, Express 5 API in `server/`, SQL Server database.

## Commands

- `npm run db:setup`: create the `VehicleInventory` database if missing, apply `server/db/schema.sql`, seed `server/db/seed.sql`, then add the 1,000 generated vehicles from `server/db/bulkVehicles.ts` (idempotent: rows are skipped by stock number)
- `npm run db:photos`: download the manufacturer press photos listed in `server/db/pressPhotos.ts` into `public/vehicles/models/` (git-ignored) and attach each to the vehicles of that make/model that have no photos yet. Idempotent; `-- --refresh` re-downloads. Run `npm run build` afterwards for `npm start`, which serves `dist/`.
- `npm run dev:api`: Express API on http://localhost:3001. Node runs the `.ts` files directly (type stripping), and `server/dev.ts` restarts the API when `server/` or `src/` changes. Don't switch back to `node --watch`: on Windows it restarts whenever a dependency lazily loads a file, which drops requests.
- `npm run user -- <name> --role admin|manager|sales|staff`: create an account or reset its password (prompts for it). Also `-- <name> --deactivate` and `-- --list`.
- `npm run db:test-teams`: test data only (not part of `db:setup`): puts `test.rep01`–`25` in teams of 5 under `test.mgr01`–`05` and sets the default salaries for those 30 test accounts from 2026-11-02 (`server/db/seedTestTeams.ts`; idempotent, needs the accounts to exist).
- `npm run agent:setup`: publish a new version of the Foundry chat agent with the instructions and tools in `server/agentTools.ts`. Tools already on the agent that aren't ours (e.g. its Foundry toolbox) are kept. Run it again after changing either; the running chat picks up the latest version.
- `npm run dev`: Vite dev server with HMR at http://localhost:5173; proxies `/api` to the API, so run both
- `npm run dev:lan`: same as `npm run dev` but reachable from phones/tablets on your Wi-Fi (`vite --host`; open the printed Network URL). Opt-in: `npm run dev` stays localhost-only. `/api` is proxied, so the API itself stays on localhost. Note that `npm start` already listens on all interfaces.
- `npm run icons`: re-render the PNG app icons in `public/icons/` from `public/app-icon.svg` and `public/app-icon-maskable.svg` with headless Edge/Chrome (`BROWSER_PATH` to override)
- `npm start`: API plus the built `dist/` front end from a single server
- `npm run build`: `tsc -b` type-check (app, vite config and `server/`), then a production build to `dist/`. Use this to verify changes.
- `npm run lint`: Oxlint (config in `.oxlintrc.json`)
- `npm run preview`: serve the built `dist/`

- `npm test`: unit tests with Node's built-in runner (`node --test server/`, files `server/*.test.ts`; pure functions, no database or Foundry)
- `cd workshop && python -m unittest -v test_agent`: unit tests for `workshop/agent.py` (Foundry client and `input()` mocked)

## Architecture

- **Data model** (`src/types.ts`): `Vehicle` interface plus `CATEGORIES`, an `as const` tuple from which the `Category` union is derived. To add a category, add it to the tuple **and** add a silhouette for it in `SHAPES` in `src/components/VehicleIllustration.tsx`; the `Record<Category, …>` type makes the build fail until you do. Condition badges are styled by class name (`.cond-<lowercase condition>` in `App.css`).
- **Database** (`server/db/`): `dbo.Vehicles` (columns `Make`/`ModelYear` map to `name`/`year`) and `dbo.VehiclePhotos` (ordered photo URLs). Category and Condition are `CHECK` constraints, so adding a category also means updating `CK_Vehicles_Category` in `schema.sql` (and writing a migration for existing databases). Schema scripts must stay re-runnable; batches are split on `GO`.
- **Connection** (`server/db.ts`): configured by `.env` (template in `.env.example`, loaded via `node --env-file-if-exists`). `DB_DRIVER=msnodesqlv8` uses ODBC + Windows auth, which works with the local SQL Express instance without TCP/IP enabled; the default `tedious` driver needs TCP and a SQL login (`DB_USER`/`DB_PASSWORD`). Always pass values as `request.input(...)` parameters, never by string concatenation.
- **API** (`server/index.ts`, queries in `server/vehicles.ts`): `GET /api/vehicles?category=&exclude=&limit=`, `GET /api/vehicles/:id` (404 when missing), `POST /api/vehicles` (201), `PUT /api/vehicles/:id`, `DELETE /api/vehicles/:id` (204), `GET /api/health`. Writes run in a transaction and replace the photo list. Errors are JSON `{ error, fields? }`: 400 for validation, 409 for a duplicate stock number, both with per-field messages in `fields`.
- **Authentication** (`server/auth.ts`): browsing is open to everyone; `POST`/`PUT`/`DELETE /api/vehicles` go through the `requireAdmin` middleware (401 signed out, 403 for `staff`). Accounts are in `dbo.Users` (role `admin` or `staff`) and are managed only with `npm run user` (`server/db/user.ts`); there's no sign-up page. Passwords are hashed with scrypt. Sessions are random tokens in an `HttpOnly; SameSite=Strict; Path=/api` cookie (`Secure` when `NODE_ENV=production`), with only their SHA-256 hash in `dbo.Sessions` (8-hour expiry). Routes: `POST /api/auth/login`, `POST /api/auth/logout`, `GET /api/auth/me`. After 5 failed sign-ins for the same username + IP, sign-in is blocked for 15 minutes (in memory). Any new write endpoint must use `requireAdmin`.
- **Passwords** (`pages/PasswordPage.tsx` at `/account/password`, admins only, linked as "Passwords" in the account bar): `POST /api/auth/password` changes your own password after checking the current one, and signs out your other sessions. `GET /api/users` lists accounts, and `POST /api/users/:id/password` resets someone else's password and signs them out everywhere. Resetting your own is refused, so it always needs the current password. Wrong current passwords count toward the same lockout as sign-in. Rules (min 10 chars, max 200, no leading/trailing space) are in `passwordProblem` in `server/auth.ts`, mirrored on the page.
- **Forgot password (no email)** (`server/passwordResets.ts`; pages `ForgotPasswordPage`, `ResetPasswordPage`): "Forgot password?" on `/login` → `POST /api/auth/forgot` records a row in `dbo.PasswordResetRequests`. It answers 202 whether or not the user exists, and allows 5 per IP per 15 minutes. Admins see open requests on the Passwords page (and a badge on "Passwords" in the account bar) and create a one-time link with `POST /api/users/:id/reset-link`. The token is 32 random bytes, only its SHA-256 is stored in `dbo.PasswordResetTokens`, it's valid 24 hours, and a new link replaces the old one. The link is `/reset-password#<token>`: the token sits in the fragment so it never reaches server logs or Referer headers. The page checks it with `POST /api/auth/reset/check` and sets the password with `POST /api/auth/reset`. Any password set (link, admin "Set password", or `npm run user`) goes through `resetPassword`, which ends the user's sessions and clears their requests and links.
- **Comments** (`dbo.VehicleComments`, `server/comments.ts`, `components/VehicleComments.tsx` on the detail page): `GET /api/vehicles/:id/comments` is public (newest first), and `POST`/`DELETE /api/vehicles/:id/comments[/:commentId]` need an admin. The author is the signed-in user. Bodies are plain text (max `COMMENT_MAX_LENGTH` = 2000), rendered with `white-space: pre-wrap`. Never render them as HTML. Comments are deleted with their vehicle; there's no edit.
- **Dashboard** (`/dashboard`, `pages/DashboardPage.tsx`, linked as "Dashboard" in the account bar): for any signed-in user (admin or staff), wrapped in `components/RequireSignedIn.tsx`. `GET /api/stats/inventory` (`requireSignedIn` middleware, `server/stats.ts`) runs one `GROUP BY Category, Condition` query and returns `InventoryStats` (total plus every category, including empty ones: count, count by condition, total value, average price/mileage/model year). The bar chart is a single series in `--accent`. Category bars and rows link to `/?cat=<category>`.
- **Customer chat** (`server/chat.ts`, `server/agentTools.ts`, `components/ChatWidget.tsx`): a floating, public widget, hidden on sign-in/admin pages and when `PROJECT_ENDPOINT` isn't set (`GET /api/chat/status`). `POST /api/chat` `{ message, conversationId? }` → `{ conversationId, reply, vehicles }` calls the Microsoft Foundry agent `FOUNDRY_AGENT_NAME` (default `vehicle-new-agent-gpt-mini`) via `@azure/ai-projects` with `DefaultAzureCredential` (`az login` locally; the identity needs Azure AI User on the project). The agent's function tools (`search_vehicles`, `inventory_summary`, `create_lead`) are declared on the agent version and **executed by our server** against SQL: the server runs up to 4 tool rounds per message. Tool arguments come from the model, so validate them like user input. Only conversation IDs the server created are accepted (in memory, 2-hour expiry). Rate limit is 20 messages per IP per 5 minutes; max 1000 chars. Azure content-filter rejections return 400 with a polite message. Replies are plain text (never HTML); the vehicles from the last search show as links under the reply (up to 5). The widget can be closed (launcher button), minimized (title bar, with a "New reply" note) or maximized; that state and the conversation are kept in `sessionStorage`. `search_vehicles` keywords match make, model, color, category and, for Electric vehicles, a body style inferred from the model name (`EV_BODY`), so "electric SUV" works; add new EV models there.
- **CRM / customer leads** (`server/leads.ts`, `server/notify.ts`, `src/leadValidation.ts`; pages `ContactPage` at `/contact`, `LeadsPage` at `/leads`, `LeadDetailPage` at `/leads/:id`; `components/LeadForm.tsx`). Customers submit first/last name, email, mobile, preferred contact (`CONTACT_METHODS`: Email/Text/Phone), New/Used/Certified, and urgency in days (1-365) from `/contact`, the "I'm interested" form on a vehicle page, or the chat agent's `create_lead` tool. All three use `validateLead` (consent is required for Text/Phone, and always for chat). `POST /api/leads` is public (honeypot field `website`, 5 per IP per 15 min shared with the chat tool via `leadThrottle`). Tables: `dbo.Customers` (one per email, holding the details from the first enquiry; insert-only, never updated), `dbo.Leads` (each lead keeps its own copy of the contact details as submitted, so a returning customer never overwrites earlier enquiries; `getLead` returns `returning` with the customer's other leads and the on-file details when they differ), `dbo.LeadFollowUps` (number 1-3, unique per lead), `dbo.LeadNotifications` (outbox/audit). Roles: `manager` (lead sales manager) and `admin` see all leads and assign them (`requireLeadManager`); `sales` reps see and work only leads assigned to them (`requireSalesTeam`, and an ownership check in `leads.ts`; other leads answer 404). Neither can edit vehicles. Status flow `New → Assigned → FirstFollowUp → SecondFollowUp → ThirdFollowUp`, then `Won`/`Lost` at any time. The 1st follow-up is due 2 days after the lead arrived, each later one 2 days after the previous follow-up was logged (`NextFollowUpDue`, overdue flagged in the UI and the "Leads" badge). After a lead is created, `notifyNewLead` emails `LEAD_MANAGER_EMAIL` and texts `LEAD_MANAGER_SMS` (an email-to-SMS gateway address) over SMTP (nodemailer; `SMTP_*` env). It isn't awaited and never throws; without `SMTP_HOST` messages are printed to the console and recorded as `Logged`. The intended provider is Brevo SMTP (`smtp-relay.brevo.com:587`, STARTTLS, login + SMTP key from Brevo, `SMTP_FROM` must be a verified sender or on a Brevo-authenticated domain, or Brevo rejects the send after accepting it over SMTP: check Brevo's Transactional logs); the code is provider-agnostic, so don't add a provider SDK. Managers can resend from the lead page. Messages are plain text, with subjects stripped of line breaks (`headerSafe`). Routes: `GET /api/leads?status=&assigned=&overdue=`, `GET /api/leads/counts`, `GET /api/leads/:id`, `PUT /api/leads/:id/assign`, `POST /api/leads/:id/follow-ups`, `POST /api/leads/:id/close`, `POST /api/leads/:id/notify`, `GET /api/sales-reps`.
- **Accounting** (`server/accounting.ts` = pure rules, unit-tested in `server/accounting.test.ts`; `server/sales.ts`; `server/payroll.ts`; pages `SalesPage` `/sales`, `RecordSalePage` `/sales/new?vehicle=&lead=`, `EarningsPage` `/earnings`, `CompensationPage` `/admin/compensation`). Earnings accounting only: no taxes, deductions or vehicle cost/profit.
  - **Sale flow**:
    - A rep (or manager) records a sale with `POST /api/sales` → `Pending`. The vehicle's `SaleStatus` becomes `SalePending`; only one live sale per vehicle (filtered unique index).
    - The seller's manager (`Users.ManagerUserId`) or an admin approves it (`/approve`) → `Approved`, the vehicle is `Sold` and a linked lead `Won`. `/reject` (with a reason) makes the vehicle `Available` again.
    - An admin can `/void` an approved sale. Nobody decides on their own sale; a manager's own sales need an admin.
    - `listVehicles`/`inventoryStats` show `Available` vehicles only, so sold and pending vehicles disappear from the inventory, chat search and dashboard. `getVehicle` still returns them (`vehicle.saleStatus`). Vehicles with sales can't be deleted (409).
  - **Rep perk**: tiered by the seller's nth approved sale in the sale's calendar month, marginal (default 1–8 $200, 9–12 $300, 13+ $400). The unit number is fixed at approval and never renumbered.
  - **Manager override**: $50 per vehicle sold by one of their reps, to the rep's manager at approval time (stored on the sale).
  - **Rates** are versioned (`dbo.CompPlans`/`CompPlanTiers`, effective date). The plan in effect on the approval date is used, and new versions can't start in the past.
  - **Salaries** are annual (`dbo.EmployeeSalaries`, effective-dated), paid ÷ 26 per bi-weekly period using the salary in effect on the period's first day.
  - **Pay periods** run Monday–Sunday × 2 from `PAY_PERIOD_ANCHOR` 2026-11-02 (`dbo.PayPeriods`, created on demand). Business dates use `DEALER_TIME_ZONE` (default America/Los_Angeles).
  - **Ledger**: `dbo.EarningEntries` is append-only; never update or delete rows, add a correcting row. Types: `Salary`, `Perk`, `Override`, `PerkReversal`, `OverrideReversal`, `Adjustment`.
    - Approval entries go into the sale date's period if it's open, else the next open period (`entryPeriod`).
    - A void reverses into the current open period.
    - Closing a period (admin, only after it ends) adds `Salary` entries and locks it.
    - A statement is the sum of a person's entries in a period; open periods show a projected salary line.
  - **Pay visibility** (`canSeePay`): self; a manager for their reps; admins everyone. Anything else is 404.
  - **Money** is `DECIMAL(12,2)` in SQL and integer cents in JS (`toCents`/`toDollars`). CSV export escapes formula-like fields (`csvField`).
  - **Weekly stats** (`GET /api/stats/sales/weekly?scope=me|team|all`), Mon–Sun:
    - From sales: units and revenue (by sale date), pending.
    - From the ledger: perks and overrides (by entry date, dealer time zone).
    - From the CRM: leads assigned, follow-ups and leads won.
  - **Routes**:
    - `/api/sales[/:id[/approve|reject|void]]`, `/api/sales/estimate`, `/api/sales/pending-count`
    - `/api/earnings/periods|statement|team|adjustments`, `/api/earnings/periods/:start/close|export.csv`
    - `/api/admin/staff|comp-plans|salaries/:userId`, `PUT /api/users/:id/manager`
- **Client auth** (`src/auth.ts`, `components/AuthProvider.tsx`): `useAuth()` gives `{ status, user, isAdmin, isLeadManager, isSalesTeam, login, logout, refresh }`. `components/RequireRole.tsx` (`RequireSalesTeam`) guards the Leads pages. Hide admin-only controls with `isAdmin`, and wrap admin-only routes in `components/RequireAdmin.tsx`, which redirects to `/login` with `state.returnTo`. Hiding controls is only for the UI; the API check is what enforces it. Navigation state (`from`, `notice`, `returnTo`) and `safePath` (blocks off-site redirects) are in `src/navigation.ts`.
- **Validation** (`src/validation.ts`): `validateVehicle` is shared by the form and the API, so the rules live in one place. It also normalizes values (trims text, upper-cases the stock number, lower-cases the hex color). It's imported by Node, so it imports with `.ts` extensions.
- **Add/edit/delete screens**: `/vehicles/new` and `/vehicles/:id/edit` both render `pages/VehicleFormPage.tsx`. Delete is an inline confirmation on the detail page (`VehicleActions`). After saving or deleting, pages navigate with `state.notice`, which `components/Notice.tsx` (rendered in `App`) shows once. The `NavState` type there describes `{ from, notice }`. Rows are mapped to the shared `Vehicle` type from `src/types.ts`, so the server and the UI use one type definition. Server code must use only erasable TS syntax and import with `.ts` extensions (`tsconfig.server.json`).
- **Client data loading** (`src/api.ts`): `fetchVehicles`/`fetchVehicle` plus the `useRemote(key, load)` hook (loading/error/ready, with retry); `components/RemoteStatus.tsx` renders the loading/error states. The inventory page loads everything once and filters client-side; filter bounds (min year, max price) are derived from the loaded data. The detail page fetches the vehicle and its "similar" vehicles separately.
- **Routing** (React Router, `BrowserRouter` in `src/main.tsx`, routes in `src/App.tsx`): `/` → `pages/InventoryPage.tsx`, `/vehicles/:id` → `pages/VehicleDetailPage.tsx`. Any unknown path also renders the detail page, which shows its "not found" state.
- **Inventory filters live in the URL query string** (`cat`, `q`, `minYear`, `maxPrice`, `sort`, `view`, plus paging `page` and `size` = 20/50/100 from `src/paging.ts`; any filter, sort or size change goes back to page 1, and an out-of-range page shows the last page), read and written via `useSearchParams`, with default values left out of the URL. Links to a detail page pass `state.from` (the current path + query), and the detail page's back link uses it so filters are preserved. Keep that pattern when adding new links into the detail page.
- **Photos**: `Vehicle.photos` is an optional list of URLs (files go in `public/vehicles/<id>/`). `src/slides.ts` turns a vehicle into gallery "slides", and `components/VehiclePhoto.tsx` renders one. When a vehicle has no photos, it uses generated SVG placeholders from `VehicleIllustration.tsx` (a category silhouette tinted with `colorHex`). Cards, gallery and thumbnails all render through `VehiclePhoto`, so real photos replace the placeholders everywhere at once; a photo that fails to load falls back to the placeholder. **Press photos** (`server/db/pressPhotos.ts`, `npm run db:photos`) are one manufacturer image per model, served from `/vehicles/models/<slug>.<ext>`; the gallery labels them "Manufacturer photo – color and trim may differ" (`isPressPhoto` in `src/slides.ts`). They're licensed by the manufacturers for editorial use, so they aren't committed. Only press sites that allow plain, unauthenticated downloads are listed: don't add browser User-Agent or Referer spoofing to get past a site that blocks the script (Toyota, Lexus and Kia do). Ford, Mercedes-Benz, BMW, Hyundai, VW, Audi, Tesla and Volvo block automated access, and Stellantis brands need a terms click-through. For those, download a photo by hand to `public/vehicles/models/` and add a row whose image is the local `/vehicles/models/…` path.
- **Formatting** (`src/format.ts`): shared `Intl` formatters for USD price and mileage; use them rather than formatting inline.
- **Responsive / mobile** (phones, iPads, desktop): breakpoints are 860px (one column) and 640px (phone; `PHONE_QUERY` and `useMediaQuery` in `src/media.ts` for JS). Touch behavior keys off capability, not width: under `@media (pointer: coarse)` form controls are at least 16px (otherwise iOS zooms in on focus) and tap targets at least 44px; hover effects (card lift, row tint, dashboard tooltips) apply only under `(hover: hover)`. Fixed elements pad with `--safe-*` (`env(safe-area-inset-*)`, from `viewport-fit=cover`). On phones:
  - The account bar collapses into a "Menu" dropdown (`AccountBar.tsx`).
  - Tables with class `table-cards` become one card per row: give each `<td>` a `data-label`, mark the title cell `cell-title`, and use `cards-only`/`cards-hide` for cells that differ.
  - The pager shows "Page X of Y".
  - The gallery supports swipe (`PhotoGallery.tsx`, `touch-action: pan-y`).
  - The vehicle page shows a sticky "I'm interested" bar once its button scrolls away.
  - The chat opens as a full-screen sheet that locks page scroll and follows `window.visualViewport` through `--chat-vh`/`--chat-top`, so the input stays above the keyboard.
  - Installable: `public/manifest.webmanifest` + icons (no service worker / offline). The "Touch and small screens" section at the end of `App.css` holds these rules.
- **Styling**: plain CSS, no framework. Theme tokens (`--bg`, `--surface`, `--accent`, …) are in `src/index.css`, with a `prefers-color-scheme: dark` override. Component styles are in `src/App.css`. Use the tokens so both themes keep working.
- **Generated inventory** (`server/db/bulkVehicles.ts`): 1,000 vehicles with stock numbers `G-00001`… from a catalog of ~190 models across 40 brands (economy to exotic). Deterministic (seeded PRNG): one of every model first, then by popularity weight. Model years stay within each model's production run (optional first/last year per catalog entry), discontinued models are never New, and exotics get low mileage. If you change the generator, existing databases keep the old rows: delete `StockNumber LIKE 'G-[0-9][0-9][0-9][0-9][0-9]'` and re-run `npm run db:setup`.
